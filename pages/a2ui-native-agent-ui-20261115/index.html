A2UI 1.0: An Open Protocol for Agent-Built Native UI

By Dekrov Published Nov 15, 2026 Updated Nov 15, 2026

A2UI 1.0 turns an agent’s proposed interface into a structured message stream that a host app maps onto its own native components. The release adds two-way function messages and accessibility metadata, but apps still own rendering, catalogs and execution policy.

Start with the plain-English explanation ↓

Overview

Google announced A2UI 1.0 on Nov 11, 2026 as the first stable release of its open protocol for generative UI. Instead of returning a screenshot, raw HTML or a wall of prose, an agent can send a structured description of an interactive surface; the client application then renders that description through components it has registered. The host keeps control of its visual system and user-facing implementation. [1]

Technical Deep Dive

How it works

A2UI is a JSON message protocol and component catalog contract, not a remote web page. The agent can create a surface, stream component definitions, update a separate data model and later delete the surface. Components refer to data through bindings such as @path; the renderer resolves those values and maps the named component to a local implementation. Keeping UI structure and application data separate lets a client update values without asking the agent to resend an entire screen. [2]

Catalogs decide what can render

A catalog is a versioned agreement about the component names, properties, allowed nesting and available functions that an agent may use. The app must register matching widgets for that catalog ID. The optional basic catalog lists 18 general-purpose components and 14 functions; teams can restyle it, extend it or replace it with a domain-specific catalog. This means “native UI” is produced by the application’s renderer, not by the agent inventing arbitrary platform widgets. [3]

Version 1.0 adds two-way function calls

In 1.0, renderer-to-agent calls can request server-side work, while agent-to-renderer calls can invoke explicitly exposed client-side functions. Each direction has a request/response message and call identifier. Catalog settings such as allowedCallers and requiresUserActivation constrain who may invoke a function and whether a direct user action is required. For example, the documentation requires the browser-opening openUrl function to be renderer-only and user-activated. The renderer is responsible for enforcing those rules; a catalog declaration by itself is not a complete security review. [4]

What shipped—and the Android caveat

Google’s launch post lists web renderers for React, Angular and Lit, Flutter across mobile, web and desktop, and SwiftUI for iOS. Jetpack Compose for Android is still listed at v0.9.1, with its 1.0 support described as forthcoming. The post also introduces TypeScript and Dart agent SDKs alongside Python, and says web and Flutter renderers can run inside MCP Apps. These are the project’s release claims; the launch post does not provide a like-for-like independent performance evaluation. [1]

License and operating cost

The public a2ui-project/a2ui repository contains an Apache License 2.0 license file. That is useful for evaluating the repository’s code, but developers should still check the license of each dependency and any separately published component package. The protocol itself does not include model inference, hosting, agent orchestration or a ready-made product UI: those costs and implementation obligations belong to the application team. [5]

Official statement

Google describes A2UI as fast and reliable and says the SDKs can reduce latency, but the launch material supplies no reproducible latency numbers, task benchmark, cost comparison or independent deployment results. Treat those as project claims rather than measured guarantees. The verifiable change is protocol scope: a stable 1.0 message format, bidirectional function RPC, accessibility/metadata support and renderer/agent SDK updates. [1] [1]

A2UI and MCP Apps solve different layers

MCP Apps provide a way for an MCP server to expose an interactive app that an MCP host can display. A2UI can supply the structured UI messages rendered inside such an app. Google says its web and Flutter renderers work in MCP Apps and points to Alation as an example; that is an implementation example reported by Google, not an independent comparison of the two standards. [1]

For teams already shipping multiple clients, a shared message format may reduce duplicated agent-to-UI glue. It does not make every client compatible automatically: catalogs and renderer implementations must agree on component versions, and the client still decides what data and actions are safe to expose. The official catalog guide recommends versioning catalogs because mismatches can change what renders. [3]

Where it fits—and where it does not

A plausible fit

A2UI is most relevant when an agent needs to return a form, comparison, planner or other interactive result across apps whose teams control the client renderer. A product can use a small allow-listed catalog so the model composes within the product’s own components instead of selecting arbitrary markup. A stable shared protocol can also make agent output portable across clients that implement the same catalog.

The work that remains

Teams still need to implement and test renderers, align catalogs across versions, connect the agent SDK, handle function responses and errors, and design authorization around data and side effects. A protocol cannot prove that a generated screen is correct, accessible in every custom renderer or safe for a particular business workflow. Google’s launch says accessibility and metadata are supported; that support is not a substitute for checking each renderer and application’s actual behavior. [2]

For a one-client app with a fixed set of screens, ordinary application UI may remain simpler. For a system that expects an agent to deliver a self-contained webpage into any host, A2UI is also the wrong mental model: it describes a bounded surface in terms of registered components rather than shipping arbitrary HTML and JavaScript.

Explained Simply

A shared format for an app screen

Think of an AI agent as a travel assistant that can either describe a trip in a paragraph or hand the app a plan for a screen: dates, choices, buttons and the data each part shows. A2UI is the shared format for that screen plan. It tells the app what components to place and how their values connect, while the app draws them using its own interface code. [2]

A catalog is a menu

The component catalog is like a restaurant menu. The agent can ask for items that the app has put on the menu—say a card, choice picker or date field—but it cannot make the client render a component that the client has not registered. That can help the product keep its own look and limit the building blocks an agent can use. [3]

Actions still need app rules

A button may also need a real action. Version 1.0 lets the screen and agent request functions from each other, but the app’s renderer must decide which functions exist and enforce the catalog’s caller and user-gesture rules. A2UI gives teams a way to describe that interaction; it does not supply their authentication, business permissions or safety testing. [4]

Conclusion

A2UI 1.0 is a meaningful step toward portable agent-generated interfaces: it stabilizes a declarative protocol, adds two-way function messages, and broadens the renderer and agent SDK ecosystem. Its practical value depends on the quality and coverage of each client’s renderer/catalog, and its function policies must be enforced in application code. Google’s announcement is the primary evidence for what shipped; the sources reviewed here do not establish independent speed, reliability, cost or coding benchmarks. If evaluating it, prototype one real workflow across the clients you support, pin a catalog version, exercise both function directions and user-activation rules, and test accessibility and failure handling in each renderer before treating the output as production-ready.
