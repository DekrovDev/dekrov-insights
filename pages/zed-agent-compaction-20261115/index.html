Zed 1.28.1 Fixes Three Long-Session Agent Failure Modes

By Dekrov Published November 15, 2026 Updated November 15, 2026

Zed 1.28.1 addresses three failures that become visible in serious agent workflows: compaction could lose prompt-cache savings, a long turn could compact only once and then overflow, and an external ACP agent could start before its configured MCP servers were available. The release also moves Zed to ACP SDK 5.0.0, but several background-work UI pieces remain unfinished.

Start with the plain-English explanation ↓

Overview

Zed released version 1.28.1 on November 11, 2026. Its AI-related changes include repeated auto-compaction during long turns, prompt-cache reuse during compaction for supported providers, better Agent Client Protocol compatibility and a fix for external agents that sometimes started without user-configured MCP servers. [1]

These are not new-model features. They change the harness around a model: how Zed keeps a thread inside its context limit, how it avoids resending an uncached prefix, and how it initializes tools for Codex, Claude, OpenCode and other external agents connected through ACP.

Project evidence

The release notes and merged pull requests establish intended behavior, code changes and project tests. They are not independent measurements of cost, latency or reliability across every provider and workflow. [1]

Technical Deep Dive

Why agent threads need compaction

A model has a finite context window. Zed tracks messages, tool calls and results inside an agent thread; as the retained history approaches the model limit, Zed can replace older material with a shorter summary. That process is compaction: it trades exact old detail for enough compressed context to continue working.

Before 1.28.1, one long agent turn—one user prompt followed by many tool calls—could trigger automatic compaction only once. If the same turn grew past the threshold again, Zed did not compact a second time and the request could eventually fail as too long. The merged fix lets the same turn compact whenever the threshold is hit and makes the next prompt try compaction after a context-length error. [4]

Why compaction could discard prompt-cache savings

Prompt caching works best when a request keeps an identical prefix. Zed’s previous compaction request disabled tools by removing their definitions. That changed the request prefix, so providers could treat the whole context as new input rather than cached input. [2]

The new strategy keeps the tool definitions in place and sends tool_choice: none when the selected provider and model support that behavior without invalidating the cache. The change is capability-gated because accepting tool_choice: none does not by itself prove that a provider preserves the cached prefix. [2]

A follow-up enabled this strategy for ChatGPT subscription models. In the pull request’s single GPT-6.1 Sol test, manual /compact changed from zero cached input tokens to 16,128 cached tokens out of 16,361 input tokens. That is a project test of one model and request, not a general cost benchmark. [3]

Compaction still has hard edges

The repeated-compaction patch explicitly leaves two cases unresolved. Manual /compact can still fail after a conversation is already beyond the model limit because the summary request itself sends the full history. A single oversized tool output can also cross the limit because Zed checks before each request, not while one result is arriving. [4]

The external-agent MCP startup race

Zed supports native Zed Agent threads, external agents through ACP and terminal threads. External agents can include Codex, Claude, OpenCode and other ACP-compatible processes; they bring their own authentication and configuration while Zed supplies the host interface. [7]

A startup race could create an ACP thread before the project’s first worktree finished loading. Zed then resolved MCP settings only through visible worktrees, found none and sent mcpServers: [] in session/new. Even after the project loaded, the already-created agent session never received those tools. [5]

The fix falls back to user-level context-server settings when no visible worktree exists. The pull request adds a no-worktree test and reports all 22 context-server integration tests passing. Behavior with one or more loaded worktrees is unchanged. [5]

ACP 5.0.0 Compatibility

Zed 1.28.1 upgrades its Agent Client Protocol dependency from SDK 3.6.0/schema 1.13.0 to SDK 5.0.0/schema 1.15.1. The port changes how missing sessions are reported, how plan updates replace old plans, how unknown diff formats fall back to structured changes and how cancellation interacts with pending permission requests. [6]

On ACP v2, cancelling a session no longer makes the client locally answer every pending permission request as cancelled. Background work may survive a session cancel, so the agent is expected to cancel the relevant request explicitly. ACP v1 keeps the older behavior. [6]

The upgrade is not a complete implementation of every new ACP surface. The pull request lists background-work UI, paused-state display, cancel buttons for tools and terminals, subagent working-directory fields and several unstable methods as follow-up work. Until the UI is added, a paused background task may still appear in progress. [6]

Evidence Analysis

What the sources establish

The stable release page confirms that these fixes shipped in 1.28.1. The merged pull requests explain the mechanisms, code paths, included tests and known exclusions. The cache-preservation PR gives one concrete token observation for GPT-6.1 Sol. [1] [3]

What they do not establish

There is no independent benchmark here comparing latency, token bills or failure rates before and after the release. The sources do not show that every long thread was affected, that every provider now caches compaction requests, or that the ACP update eliminates all external-agent incompatibilities.

Maintainer test

The 16,128 cached tokens out of 16,361 input tokens are useful mechanism evidence, but they are a single maintainer-reported run with GPT-6.1 Sol. Treat the number as a reproduced project example, not a universal savings percentage. [3]

Practical Impact

  1. Update to Zed 1.28.1 or later if you keep long agent turns, use ChatGPT subscription models or run external ACP agents with MCP tools.
  2. Do not assume compaction makes context unbounded. Large single tool outputs and already-over-limit manual compaction remain failure cases.
  3. Check MCP tools after external-agent startup. The race is fixed, but confirming the expected tool list is still a useful integration check.
  4. Measure cache usage per provider. The same request shape can produce different caching behavior, and Anthropic is explicitly outside this implementation path.
  5. Expect partial ACP 5 UI coverage. Protocol compatibility improved before every background-work control reached the interface.

Explained Simply

The notebook problem

Imagine an agent keeps a notebook of everything you said and every tool result. When the notebook is almost full, Zed writes a shorter summary and starts a cleaner notebook. That is compaction.

Before this release, Zed might summarize once during a very long task and then refuse to summarize again until the turn ended. If the agent kept using tools, the notebook could still overflow. Version 1.28.1 lets the same long turn summarize again when needed.

Why the summary could cost more than expected

Providers can reuse an unchanged beginning of a prompt from cache. Zed used to remove tool definitions while requesting a summary, changing that beginning and potentially losing the cache. For compatible models, it now keeps the definitions identical and says not to call them.

Why an external agent could miss its tools

If Zed launched an external agent before the project folder finished loading, it could send an empty MCP-server list even though the user had configured servers globally. The release now falls back to those user settings until a worktree exists.

The result is a more reliable long-session harness, not infinite context or guaranteed savings. Very large outputs, unsupported providers and unfinished ACP background controls still matter.

Conclusion

Zed 1.28.1 is a maintenance release with unusually practical consequences for agent-heavy development. It repeats compaction inside long turns, preserves prompt-cache prefixes where the provider contract permits it, prevents a worktree-loading race from stripping MCP tools and aligns external agents with ACP SDK 5.

The strongest improvement is architectural: the harness now distinguishes model limits, cache capabilities and protocol lifecycle more carefully. The remaining limits are equally important—Anthropic is outside the cache strategy, oversized tool results can still overflow context, and the ACP background-work UI is incomplete.
