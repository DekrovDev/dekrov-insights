Plurai Simulation Builds Stateful Worlds to Test AI Agents

By Dekrov Published Nov 15, 2026 Updated Nov 15, 2026

Plurai Simulation turns an agent’s code and selected data into a versioned test suite with simulated users, stateful mock tools and outcome checks. We examine how the local runner and hosted backend fit together, what the vendor’s evidence does and does not show, and where conventional tests still matter.

Start with the plain-English explanation ↓

Overview

Plurai launched Simulation on November 11, 2026 as a way to test an AI agent against a small, stateful version of the world it acts on. Its announcement says the tool builds mocked tools, simulated users and evaluations from an agent’s code and optional data, then runs the agent through scenarios. The product is available through plugins for Claude Code, Codex and GitHub Copilot CLI; Cursor is listed as coming soon. The company says it is free to start, but the public launch page gives no exact usage limits or ongoing price. [1]

Technical Deep Dive

Scan first, then build the scenario

The workflow begins with a coding-agent plugin that scans the agent’s repository and maps the tools, APIs and knowledge stores it uses. The agent proposes which systems to mock and which to leave real; a developer reviews that choice. After approval, the workflow writes a plurai_sim/ folder containing configuration, a plain-language description of the agent, a standalone simulate.py harness and scenario variables such as records, user types and complications. [2]

A shared world state is the key design choice

In a realistic support scenario, the customer’s claim, the order record, the payment tool and the expected outcome must agree. If an agent refunds a duplicate charge, a later order lookup should show that refund. Plurai says it generates a seeded state for each scenario and makes every mocked tool read and write that same state; code checks can then inspect the final state, while model judges handle questions that need interpretation. [2]

This makes the test about the agent’s actions and their consequences, rather than only whether its final message sounds plausible. The vendor says it validates that scenario IDs exist in the seeded records, checks whether a scenario can be solved, and uses a critic on a qualification run before assembling the suite. Those are descriptions of the product’s own process; no independent audit of the generator was found. [2]

What runs locally, and what reaches the backend

The architecture has three pieces: a coding-agent plugin that reads the repository and talks to Plurai over MCP; a local SDK that starts the real agent and drives its turns over REST; and a Plurai backend that builds the world graph, scenarios, evaluations and mock services. The company says the agent, model keys and tool credentials stay on the developer’s machine. It also says the backend receives the generated plurai_sim/ folder, any optional sources a user chose to provide, and the simulated conversation during a run. [2]

Optional inputs include production traces, a knowledge base or database, and example records or documents. These can make a test more specific, but they also change the data being sent to the service. Before using real customer material, teams should review the data terms and retention settings, minimize or redact sensitive fields, and confirm which sources are included. That is a practical consequence of the vendor-described data flow, not a claim that Plurai mishandles data. [2]

Where it fits beside other evaluation methods

Different tests answer different questions
MethodBest question it answersMain blind spot
Unit and contract testsDoes a component or integration follow a specified behavior?They do not, by themselves, explore an agent’s open-ended multi-turn decisions.
General agent benchmarkHow do models or agent systems perform across shared interactive tasks? AgentBench, for example, uses eight environments.A general benchmark does not encode one company’s private tools, policies or records.
Plurai SimulationHow does this agent behave in generated, project-specific scenarios with shared mock state?The result depends on the quality and coverage of the generated world and evaluations.
Production trace replayDoes a known real failure still happen, or did a targeted fix address it?It only covers failures and paths represented in the traces supplied.

These approaches are complementary. AgentBench is a research benchmark for comparing agents across common environments; Plurai describes a project-specific test suite that can reuse a versioned world and replay selected production traces. Neither removes the need for deterministic unit, contract and staging tests. [2][4]

Access, license and evidence

The November 11 announcement says Simulation is free to start and names Claude Code, Codex and GitHub Copilot CLI integrations, with Cursor marked as coming soon. The pages reviewed do not state a full pricing schedule, usage caps or a license for the hosted service, so none should be inferred from “free to start.” [1][3]

Vendor-reported results

Plurai’s launch post says design partners saw agent-development cycles fall from months to hours and failures reaching users fall by 82%. It does not publish the sample size, baseline definition or evaluation method alongside those figures. Treat them as company-reported claims, not an independent result or a general forecast. [1]

Evidence & Limits

The product architecture and claimed checks above come from Plurai’s own technical post and FAQ. They explain how the system is intended to work, but they do not independently establish scenario quality, regression detection rates or production outcomes. [2][3]

A stateful mock can expose mistakes that a transcript-only score misses. It can still differ from the real service’s timing, permissions, rate limits or undocumented behavior. That is an inference from the difference between a simulated environment and production; it is why contract tests and a safe staging environment remain useful alongside simulation.

Community Reactions

In the public sources checked for this launch, I found the vendor’s announcement, implementation description and FAQ, but no independent evaluation or detailed user report of Plurai Simulation itself. That leaves adoption, reliability and the vendor’s outcome figures unverified. It is a gap in available evidence, not proof that the product does not work.

Explained Simply

Imagine testing a delivery assistant. You tell it that a customer was charged twice. A weak test checks only whether the assistant apologizes. A better test gives it a pretend order and payment system, lets it issue a refund, and checks whether the order record really changed.

Plurai’s idea is to build that pretend world from the agent’s code, then ask a coding agent to create customer scenarios and checks around it. The real agent runs locally, while the vendor says its service prepares and hosts the simulated tools and scenario.

This can help find mistakes before a real user sees them. But a pretend system is still a model of reality: it can miss a behavior the real payment or database service handles differently. Keep ordinary tests, review the generated scenarios, and use carefully chosen real traces or staging checks where appropriate.

Conclusion

Plurai Simulation targets a real gap in agent testing: multi-step systems need tests that keep users, tools and data consistent across a conversation. Its local runner, generated stateful mocks and versioned scenarios are a concrete design worth evaluating for agents that take consequential actions. Start with non-sensitive fixtures, inspect the generated suite, and compare it with known failures and deterministic tests before relying on its pass rate. Public evidence is still vendor-led; independent results and exact paid-plan limits remain unknown.
