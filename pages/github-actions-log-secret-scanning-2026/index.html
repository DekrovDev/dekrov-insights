GitHub Starts Scanning Actions Logs for Secrets — What the Preview Misses

By Dekrov Published Nov 10, 2026 Updated Nov 10, 2026

GitHub's new workflow-log secret scanning preview closes a visibility gap, but its limitations and lack of notifications deserve as much attention as the announcement.

Start with the plain-English explanation ↓

Overview

On November 9, 2026, GitHub announced a public preview that checks completed GitHub Actions workflow logs for supported leaked credentials. Unlike source-code scanning, this looks at output produced during automated builds and tests. The change matters because a token can be printed during a job without ever appearing in a committed file. [1] [2]

The preview is not a universal free feature, not an instant leak-prevention system and not a substitute for credential hygiene. Past CI supply-chain incidents explain why the surface matters, but do not prove how well this new scanner performs. [3] [4] [5]

Technical Deep Dive

How it works

When an eligible workflow run finishes, GitHub scans its log for recognized provider patterns. A match creates a repository secret-scanning alert with a link to the workflow and log location; supported credential types may receive validity checks. Alerts persist even if logs are later deleted. Scanning occurs after the job, so exposure may have happened already. [1] [2]

Availability

GitHub says this preview is for GitHub Enterprise Cloud enterprises with GitHub Secret Protection or GitHub Advanced Security, including supported GHE.com deployments. An enterprise owner can go to Settings → Policies → Advanced Security and enable scanning for Actions workflow logs for all repositories. It is disabled by default and only covers repositories with licensed secret scanning enabled. [1]

Why these limits matter

Alerts do not send notifications in the preview; maintainers need to inspect the secret scanning alert list themselves. Masked secrets and transformed values are outside this specific detection path. GitHub's own runner-security documentation warns that log masking is not a security boundary: a compromised job may access credentials before redaction or send them elsewhere. [1] [2] [3]

Real-world context, carefully separated

Reporting on the March 2025 tj-actions/changed-files compromise described sensitive build data exposed through Actions logs. An October 2026 Cloud Security Alliance analysis described the Gheist campaign's use of encoded log output to extract credentials. [4] [5]

Neither historical case proves the November 2026 scanner would have detected that attack; encoded values can evade pattern matching and no independent evaluation of the preview was found in the reviewed sources. [3] [4] [5]

Official statement

Feature behavior and plan eligibility are GitHub's published claims. No independent sensitivity test, false-positive study or hands-on Dekrov detection run is asserted here. [1] [2]

What to do

Eligible enterprise administrators can enable the preview and establish manual alert review. When a credential is exposed, revoke or rotate it promptly and investigate its permissions and use. [2]

Independently of eligibility, use least-privilege workflow tokens, prefer short-lived credentials where possible, review third-party Actions, and avoid printing environment secrets in build output. This feature detects some mistakes after they occur; it does not prevent every exfiltration route. [2] [3]

Official statement

GitHub documents feature behavior and exclusions; independent detection performance has not been established. [1]

Explained Simply

Picture an automated robot building an app. Every time it works, it writes a diary of its actions. That diary is a workflow log. Sometimes a robot accidentally writes down a password or access key. Someone with access to that diary might copy it.

GitHub already checks project files for some exposed keys. Now, in a limited preview, it can check the robot's diary too. If it recognizes a supported key, it places a warning in the repository's security alerts. This matters even when the key never appeared in the code itself. [1] [2]

There is an important catch: the check happens after the robot finishes. It cannot take back a key somebody already saw. It also skips old diaries, several kinds of key patterns and already masked values. It does not send notifications during this preview, so somebody must look for the warnings. [1] [2]

For now, only qualifying paid GitHub enterprise customers can switch this on. Everyone else should still avoid printing passwords, give automation limited permissions, and replace any credential suspected of leaking. The scanner is an extra smoke alarm, not a lock on the door. [1] [3]

The diary analogy explains why CI logs can expose credentials even without a code commit.

The preview has plan restrictions and important exclusions; reduce credential exposure regardless of availability.

Conclusion

This is a useful new detection surface for enterprise CI/CD security: certain credentials in newly completed workflow logs can trigger alerts. But the exclusions are significant, and the preview's effectiveness has not been independently quantified in the sources reviewed. Teams should enable it where eligible, monitor alerts manually and continue designing workflows to minimize credential exposure. [1] [2] [3]
