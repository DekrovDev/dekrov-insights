GitHub AI Scan Gains REST Controls for Repository-Level Rollouts

By Dekrov Published Nov 15, 2026 Updated Nov 15, 2026

GitHub has added a REST API setting for AI Scan on full repositories. Organizations can now manage rollout through scripts or infrastructure as code, but enabling the feature does not launch a scan, and the preview remains subject to enterprise policy and AI-credit costs.

Start with the plain-English explanation ↓

Overview

On November 13, 2026, GitHub announced that its existing AI Scan enablement endpoints now accept a `repository_scan` setting. The change lets eligible organizations control the repository-backlog scan at organization and repository scope through REST, alongside the existing pull-request setting `pr_scan`. It turns a click-through security setting into something teams can version, audit and roll out consistently. [1]

Technical Deep Dive

How it works

The public-preview API exposes `GET` and `PATCH /orgs/{org}/code-scanning/ai-scan` and `GET` and `PATCH /repos/{owner}/{repo}/code-scanning/ai-scan`. The new `repository_scan` value is `enabled` or `disabled`. An organization-level enablement flows to eligible repositories, whose administrators can opt out; if the organization disables it, a repository cannot enable it locally. Enterprise policy still takes precedence. A `422` policy or validation failure leaves both `repository_scan` and `pr_scan` unchanged when they were sent together. [2]

Official statement

GitHub’s release note and API reference establish that the setting can be managed through REST in public preview. They do not say that a request starts a scan or that scans are exhaustive. A scan is still run on demand by a user with write access, and each run consumes AI credits. [1][3] [1]

Explained Simply

AI Scan is a GitHub code-security feature that uses an AI agent to look for vulnerabilities across a repository’s default branch. A REST API is a machine-readable way for scripts and tools to read or change a service setting. GitHub’s change adds a switch for repository-level scans to the API that already managed AI Scan for pull requests.

Think of an organization setting as a building’s main switch and each repository as a room. The organization can turn the feature on for eligible repositories, while a repository administrator may opt out. An enterprise policy can still keep the main switch locked. This makes a large rollout easier to repeat and review, but it does not make the scan automatic.

The scan itself is more like a focused inspection than a guarantee that every line was checked. GitHub says scans cover only the default branch, must be triggered manually, do not support self-hosted runners, and may miss vulnerabilities or produce inaccurate findings. Review alerts, keep CodeQL and ordinary tests in place, check AI-credit budgets, and verify your organization’s enterprise policy before automating enablement. [3][4]

Conclusion

The confirmed change is a public-preview control plane for enabling or disabling repository AI Scan at organization and repository level. It improves repeatability, not scan coverage or detection quality. Teams should treat it as configuration automation: check policy and eligibility, budget AI credits, stage the rollout, then trigger and review scans separately. GitHub has not published an independent evaluation of this API change or evidence that it improves vulnerability detection.
