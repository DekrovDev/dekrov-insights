Claude Code’s MCP OAuth Redirect Bug

By Dekrov Published November 15, 2026 Updated November 15, 2026

Claude Code 2.1.321 closed a cross-host redirect flaw in its MCP OAuth flow. An independent loopback test found that 2.1.319 could preserve sensitive form data across a 307 redirect and deliver an authorization code, PKCE verifier and refresh token to a second host. The patch is real; the full affected-version range and any real-world exploitation remain unknown.

Start with the plain-English explanation ↓

Overview

Anthropic released Claude Code 2.1.321 on November 9, 2026. Its release notes say the version fixed MCP OAuth requests that could send secrets “such as refresh tokens” to another host when a server redirected them. [1]

That one-line note describes a credential-boundary failure, not merely an inconvenient redirect. A refresh token can often be exchanged for fresh access tokens until it expires or is revoked, so sending one to the wrong origin can outlive the original login request.

Official statement

Anthropic confirms the flaw class and the fixed release. The note does not name a CVE, assign severity, identify the first affected version, describe victims or claim observed exploitation. [1]

Technical Deep Dive

Where OAuth enters an MCP connection

The Model Context Protocol lets a client connect to remote servers that expose tools and data. When a server requires OAuth, Claude Code acts as the client: it discovers authorization metadata, opens an authorization flow and later sends a token request to the advertised token endpoint.

OAuth separates several values with different jobs. An authorization code is short-lived and exchanged for tokens. The PKCE verifier proves that the client completing the exchange is the same client that started it. A refresh token can request new access tokens without asking the user to sign in again.

The reproduced redirect chain

Gloss researcher Marco Kotrotsos tested Claude Code 2.1.319 against a fake MCP server on loopback. In 18 scripted runs, the token endpoint returned an HTTP 307 redirect to a second host. A 307 tells the client to repeat the request with the same method and content, which is useful for legitimate same-origin routing but dangerous when the destination origin changes. [2] [4]

In that test, Claude Code followed the cross-host redirect. The second host received the authorization code and PKCE verifier during the initial token exchange, then the refresh token during a later refresh. The client stripped the Authorization header, but the secrets were in the form body, so removing the header did not protect them. [2]

Why PKCE did not save this flow

PKCE is designed to stop an intercepted authorization code from being redeemed by someone who lacks the verifier. Here, the client itself sent both the code and the verifier to the redirected host. A control cannot protect a secret after the trusted client forwards all of the ingredients across the boundary it was meant to enforce.

The MCP authorization security guidance separately warns about mix-up attacks and open redirection. It requires exact redirect-URI validation by authorization servers and validation of authorization responses by clients. Those requirements address related trust-confusion risks; they do not prove that every compliant MCP deployment was exploitable through this particular Claude Code behavior. [3]

What the patch changed—and what it did not establish

The independent retest reports that 2.1.321 and 2.1.322 refuse the cross-host token request and identify both hosts in the error, while legitimate same-host redirects still work. That is a narrower and more useful fix than disabling every redirect. [2]

Neither the release note nor the reproduction establishes the first vulnerable version, the complete set of affected configurations, a CVSS score or exploitation in the wild. The defensible statement is therefore specific: 2.1.319 was reproduced as vulnerable in the published test, and 2.1.321 is the official fixed release.

Evidence Analysis

What is confirmed

The vendor confirms the vulnerability class and fix version. The independent test provides request-level behavior for 2.1.319, 2.1.321 and 2.1.322, including which secrets crossed hosts and which redirect cases still worked. The HTTP standard explains why a 307 normally preserves the request method and content. [1] [2] [4]

What is not confirmed

No cited source reports a victim, a malicious MCP server used in production, a stolen token being redeemed, a CVE or a vendor severity score. The test demonstrates a viable mechanism under controlled conditions; it is not evidence that the mechanism was exploited against users.

Independent test

The 18 runs used a fake MCP server and two loopback hosts. That makes the redirect behavior reproducible without exposing real credentials, but it cannot estimate prevalence or incident count. [2]

Practical Response

  1. Update Claude Code to 2.1.321 or later. Prefer the current release rather than pinning to the minimum fixed build.
  2. Inventory remote MCP servers that use OAuth. Record the MCP host, authorization-server host and any expected same-origin redirect behavior.
  3. Investigate unexpected cross-host redirects. Review client, proxy and authorization-provider logs if available. A redirect alone is not proof that a token was used.
  4. Revoke the affected grant when exposure is plausible. Revocation or provider-side rotation is stronger than merely logging in again; provider behavior varies.
  5. Keep redirect policy origin-aware. Same-host infrastructure redirects may be legitimate, while a changed scheme, host or port deserves an explicit trust decision.

Explained Simply

A forwarding address for a sealed envelope

Imagine Claude Code is carrying a sealed envelope to the login desk for an MCP tool. The desk replies, “Take the same envelope to this other address.” A normal redirect can be harmless when the other address belongs to the same building, but the old behavior did not stop when the destination belonged to a different host.

The envelope could contain an authorization code, a PKCE verifier and later a refresh token. The refresh token matters most because it may let its holder request new access tokens after the original access token expires.

What changed

Version 2.1.321 added the missing boundary check: a token request is not silently repeated to another host. Tests indicate that redirects within the same host still work, so normal routing does not have to be broken to prevent the leak.

What users should do

Update Claude Code. If you connected to an OAuth-enabled MCP server through an older build and have evidence of an unexpected host redirect, revoke that authorization grant and review activity with the provider. There is no evidence in the cited material that every older login was compromised or that this was exploited in the wild.

Conclusion

This was a real client-side trust-boundary bug with a narrow, testable fix. Anthropic’s release note confirms that 2.1.321 stopped MCP OAuth secrets from crossing to another host after a redirect, and an independent loopback harness shows how 2.1.319 could leak form-body credentials through a 307 while stripping only the header.

The responsible takeaway is precise rather than dramatic: update, examine unexpected redirect paths and revoke grants when exposure is plausible. Do not turn a reproduced mechanism into an unsupported claim of mass exploitation; the full affected range, severity rating and real-world incident count remain unknown.
