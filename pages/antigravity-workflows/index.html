Antigravity Dynamic Workflows Give Coding Agents Scripted Control Flow

By Dekrov Published November 16, 2026 Updated November 16, 2026

Google’s Dynamic Workflows coordinate parallel and staged coding tasks in a local Python script with structured results.

Start with the plain-English explanation ↓

Overview

Google’s current App and CLI documentation describes Dynamic Workflows for Google AI Pro and Ultra. A generated Python script sets the order of work, starts agents in their own conversations and receives structured results. The workflow can run in the background after approval, and Antigravity bundles a Python interpreter. [1]

Technical Deep Dive

How it works

parallel() handles independent items. pipeline() sequences stages that depend on one another. An agent can work once or retain its conversation across stages. When the script specifies a JSON Schema, the agent’s result is checked against it before the script receives the value. The schema checks the result’s shape. A correctly shaped report can still contain an incorrect diagnosis. [1]

Official statement

Google documents the execution model and supported plans. We found no comparable independent timing or quota measurements for this workflow feature. [1]

Review the script and workspace scope

Antigravity normally presents the generated script for approval; the configured permission preset can change that step. The workflow has named phases and individual agent conversations. Google documents a worktree option for isolation. That choice matters if multiple workers would otherwise edit the same files. A clean worktree per worker still leaves integration and test ownership to the workflow designer. [1] [2]

The bundled Python runs in a separate process. The first workflow may spend time unpacking it. Google documents fallback to an installed Python when the bundled runtime cannot start, as well as an interpreter override. App and CLI support is documented on Pro and Ultra. The published guide does not establish a free entitlement or provide a per-workflow cost figure. [1]

When scripted control helps

Choosing how to split a coding task
ApproachGood fitTrade-off
One sessionA small change with one tight feedback loopFewer moving parts, with every step handled serially by one agent.
Background subagentsIndependent investigations alongside a parent task [3]The parent interprets reports as they come back.
Dynamic WorkflowRepeatable parallel checks followed by a shared verification stage [1]The script defines the order and report shape. It adds coordination overhead and needs review.

For a practical trial, give each worker a different package to check for regressions, then run the same integration suite once after collecting the reports. Record which tests actually ran and require file references for each finding. Compare the result with a single-agent run at the same scope. Neither the availability of more workers nor a schema-compliant report establishes a speedup or a passing build.

Explained Simply

Say an update changes four packages. The main agent can generate a script that starts four separate reviewers together. Each reviewer checks its package and returns the same fields, such as file, finding and test outcome.

The script can wait for all four reports and then run a single test phase. This makes it easier to see who checked what and which checks still need to finish. The parent conversation can keep its summary without loading every worker’s raw logs.

Use separate workers when tasks can proceed independently. Use a sequence when the next change needs the previous result. Review the script and tool permissions, and require concrete test results before accepting its summary.

Conclusion

The feature is best suited to repeatable reviews, independent package changes and staged verification. Compare the same task in a single session and a workflow using elapsed time, confirmed test outcomes and usage. If edits are needed, keep initially independent work in separate worktrees and define how to integrate it. [1] [2]
