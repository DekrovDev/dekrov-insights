wfx-loot: How Hijacked GitHub Accounts Turned CI into a Credential-Theft Path

By Dekrov Published November 15, 2026 Updated November 15, 2026

wfx-loot is a November 2026 supply-chain campaign in which attackers used stolen GitHub credentials to plant a credential stealer in CI workflows and package installation hooks. The hard lesson is that a trusted commit author is not proof that the commit is safe.

Start with the plain-English explanation ↓

Overview

On November 12, Aikido Security described a campaign it named wfx-loot: attackers used compromised developer accounts to probe and modify repositories, then inserted code intended to run inside continuous integration (CI) jobs. CI jobs often receive credentials for source control, cloud deployment and package publishing, so a brief workflow change can expose much more than the repository itself. Aikido’s report describes 4,837 accounts and 61,764 repositories probed, with malicious execution indicated in roughly 1,800 repositories. Those are its measured counts and should not be read as a complete census. [1] [1]

Technical Deep Dive

How it works

The reported activity began around November 10. Stolen credentials let the attacker act through real accounts that already had repository write access. The resulting changes looked like routine maintenance: innocuous pull-request or commit wording, a workflow edit, a helper script, or a package install hook. If a repository’s automated checks ran that code, it could inspect the job environment and attempt to collect credentials available to that process. Aikido says the operator quickly reverted changes and deleted workflow runs and logs, making run-history gaps a useful clue. [1]

Endor Labs independently documented the same broad campaign and reported more than 8,900 repositories containing its “wfx” change, with over 829 package manifests receiving install hooks. Its article was updated November 13 with additional observations. That repository-search figure is not a directly comparable count of Aikido’s 61,764 probes: one describes repositories in which Endor found a change, the other includes repositories probed. The public reports do not establish a single harmonized total. [2]

Official statement

Aikido’s incident report provides campaign indicators, an account/repository probe count and an estimate of observed executions. Endor Labs independently describes the credential-theft workflow and its own repository findings. These are investigator measurements from different collection methods and times, not a GitHub-wide audit or a guarantee that unlisted repositories were unaffected. The reports attribute the intrusion to stolen account credentials; they do not identify a GitHub Actions platform vulnerability. [1] [2] [1]

Why the numbers differ

A probe is not the same event as a malicious commit, and neither proves that a workflow executed. A repository search can also depend on when it ran and which surviving commits or package files it can still observe. Aikido and Endor Labs describe overlapping activity but use different scopes. Keep each number attached to its publisher and definition; adding them or presenting one as the final affected-repository count would be misleading. [1] [2]

A response checklist for maintainers

  1. Search organization-wide for the suspicious PR/branch/commit patterns listed by the researchers; inspect workflow files, shell helpers and package lifecycle scripts changed since November 10. [1]
  2. Review Actions run history around those changes for missing or deleted runs. A gap is a clue to investigate, not independent proof that the stealer ran. [1] [2]
  3. Revoke suspected GitHub sessions, personal access tokens and other credentials associated with the compromised account. Secure the account and check its recent activity.
  4. If malicious code executed, assume every credential available to that job may have been exposed. Rotate those credentials, then inspect cloud role trust and federation settings for persistence. [1] [2]
  5. Reduce future blast radius: grant workflows only the permissions they need, avoid exposing secrets to untrusted pull-request code and review changes to workflow files as privileged code. GitHub’s hardening guide explains these controls. [4]

Do not run suspicious scripts to “test” whether a repository is affected. Preserve evidence and follow your organization’s incident-response process.

Explained Simply

A CI pipeline is a robot that builds and checks code whenever someone changes a project. To do its job, the robot may be allowed to read private files, publish a package or deploy to a cloud account. A secret-stealing change tries to make that robot send those credentials away while it runs. [1] [2]

Imagine someone borrows a maintainer’s badge and slips a new instruction into a warehouse checklist. The checklist is trusted and the worker follows it; the worker also has keys to rooms the intruder cannot enter directly. In this incident, the “badge” was a compromised GitHub credential and the “worker” was CI. That is why a tiny-looking repository edit can put software releases and cloud systems at risk.

Start by searching every repository the affected account or organization can write to—not only the repository where a suspicious change was first spotted. Aikido lists suspicious pull-request and commit wording, branches and package hooks; Endor also advises checking for missing workflow run numbers after November 10. These indicators are leads, not proof by themselves. [1] [2]

If you find evidence that the payload ran, preserve the remaining logs and repository state, revoke compromised GitHub credentials, then rotate every secret the affected workflow could access. Check cloud identity policies and newly created federation credentials as well: changing a password or token alone may not remove persistence. GitHub’s Actions hardening guidance recommends least-privilege workflow permissions and careful handling of untrusted changes, but those controls do not substitute for incident response. [3] [4]

Conclusion

The supported conclusion is specific: attackers abused compromised GitHub accounts to introduce credential-stealing code into CI-related execution paths. The reports agree on the core mechanism but count different parts of the campaign, so their repository totals should remain attributed and qualified. Teams should audit recent workflow and package-manifest changes, review Actions history for unexplained gaps, revoke suspected compromised tokens, and rotate all reachable credentials if code executed. A matching pull request title alone is not proof of compromise; an apparently clean repository is not proof that no credentials were exposed. [1] [2]
