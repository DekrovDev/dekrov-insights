Dependabot Alerts Will Pause on Inactive Repositories

By Dekrov Published Nov 12, 2026 Updated Nov 12, 2026

A repository can stop receiving commits while its software remains in use. GitHub’s upcoming alert policy makes that distinction important.

Start with the plain-English explanation ↓

Overview

GitHub announced on November 10 that starting December 8, 2026, most repositories without qualifying activity for a year will lose active Dependabot alert coverage. Previous findings will be retained for restoration. [1]

A stable library can still be deployed or consumed by other projects. Its dependencies may acquire newly disclosed vulnerabilities even if its own code has not changed.

Technical Deep Dive

The activity clock

Repository creation, enabling alerts and pushes to branches or tags count as activity. A push or manual reactivation restores archived findings and resets the clock. [1]

Illustrative scenarios, not rollout tests.
ScenarioExpected result
Year without qualifying activityPause for most repositories [1]
Push or enable alertsRestore findings and restart clock [1]
Enforced configuration enabling alertsExempt from pause [1]

Exceptions and scope

Enterprise policies preventing repository administrators from toggling alerts also exempt repositories. The policy covers GitHub.com and Enterprise Cloud with data residency, not Enterprise Server. [1]

Official statement

GitHub cites increasing vulnerability and alert volume as motivation. It does not quantify the performance improvement or affected repository count. [1]

Alerts versus updates

Dependabot separately provides vulnerability alerts, security-update pull requests and routine version-update pull requests. The announcement concerns alerts; it does not establish that all scheduled version updates will stop. [3]

A practical audit

  1. Inventory quiet repositories still producing deployed artifacts.
  2. Check the actual alert setting and review open findings in Security and quality. [2] [3]
  3. For critical organization repositories, evaluate enforced security configurations. [1]
  4. Assign an owner for periodic dependency reviews and maintain a deployed-version inventory.

These are recommendations, not evidence that the upcoming rollout has already occurred. An alert service is only one part of dependency maintenance.

Explained Simply

Imagine a smoke alarm in a storage room nobody visits. The room may still contain valuable equipment even if nobody opens its door for a year. GitHub's upcoming policy is similar to pausing that alarm for many quiet repositories.

Dependabot alerts tell maintainers about known vulnerabilities in software packages they use. A project can remain unchanged while the outside world discovers a flaw in one of those packages. Quiet code is not automatically safe code.

If your repository falls under the new policy, pushing or re-enabling alerts restores archived findings. Some enterprise-managed repositories are protected from the pause by policy. [1] If you still use an old project, check its settings and give someone responsibility for reviewing dependencies rather than creating meaningless commits.

Conclusion

The policy is announced, not yet effective on November 12. Track repository activity separately from software exposure. The documented restoration path is useful, but actual rollout behavior and aggregate impact remain untested here. [1]
