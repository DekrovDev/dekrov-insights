Agent Skills Are Portable—Execution Isn’t

By Dekrov Published November 15, 2026 Updated November 15, 2026

GitHub’s new practical guide frames Agent Skills as reusable workflows that can move between agents. The file format is genuinely portable; the execution environment is not. This investigation separates the shared standard from the host-specific paths, permissions, tools and security boundaries in Codex, GitHub Copilot, VS Code and OpenCode.

Start with the plain-English explanation ↓

Overview

On November 12, 2026, GitHub published a practical guide to Agent Skills: versioned directories centered on a SKILL.md file that package repeatable instructions, scripts and resources. GitHub also states the critical limit directly: the destination environment must still provide the tools, credentials and permissions required to execute the workflow. [1]

The open specification makes the instruction package portable. It does not promise identical activation, tool names, confirmation prompts, filesystem access, network policy or results across hosts. “Build once” is therefore a useful authoring goal—not proof of behaviorally identical execution.

Technical Deep Dive

The portable core

A conforming skill is a directory containing SKILL.md. Its YAML frontmatter requires a lowercase, hyphenated name and a non-empty description; optional fields include license, compatibility, metadata and experimental allowed-tools. The directory may also contain executable scripts, references and assets. [2]

The design uses progressive disclosure. A host can load only names and descriptions during discovery, read the full instructions when a skill activates, and open supporting files only when needed. The specification recommends keeping SKILL.md under 500 lines and references one level deep to control context cost. [2]

Official specification

The format repository is public. Its code is Apache-2.0 and its documentation is CC-BY-4.0. The repository describes Agent Skills as an open format originally developed by Anthropic and now governed through the Agentic AI Foundation. [3]

VS Code explicitly says portability is subject to each agent’s supported locations and features. Its current documentation covers Copilot in VS Code, Copilot CLI, the Copilot app and an experimental Codex integration. [4]

OpenCode searches several compatibility paths but adds its own catalogs, duplicate-ID precedence and permissions. It advertises descriptions to the model and loads full instructions with its skill tool, rather than injecting every skill into every prompt. [5]

Copilot CLI recognizes overlapping project paths, but its execution control is distinct: a missing tool approval can trigger a prompt, while pre-approving shell or bash can remove the confirmation step. GitHub warns users to do that only after reviewing the skill and its scripts. [6]

OpenAI draws a similarly important boundary: an MCP server provides live data, authentication, authorization and actions, while a skill describes when and how to combine those capabilities. Copying the skill does not copy the MCP connection or its access. [7]

The portability security trap

A skill is not merely a prompt file. It can bundle executable code, templates and references. That makes installation closer to adding a small dependency than pasting harmless instructions. A malicious or compromised skill can request dangerous tools, hide behavior in scripts, or exploit broad host permissions.

  1. Review SKILL.md and every referenced script before installation.
  2. Pin a release or commit instead of following an unreviewed moving branch.
  3. Validate the package with the reference validator where possible.
  4. Keep shell, network, secret and write permissions narrow.
  5. Test activation and output in every intended host; do not assume cross-host equivalence.

OpenAI’s API documentation makes the same trust point explicit: skills should be treated as untrusted input until their contents and behavior have been validated. [8]

What the Evidence Does—and Does Not—Prove

The official sources agree on the directory format, progressive loading and broad portability goal. They also document concrete differences in search paths, catalogs, permissions and integrations. That is strong evidence for syntactic portability.

There is no independent benchmark here showing that one skill produces equivalent decisions, tool calls or outputs across Codex, Copilot, VS Code and OpenCode. Model choice, system instructions, available tools and security policy can all change the result. Claims of “run anywhere” should therefore be read as compatibility with the package format, not deterministic behavioral parity.

Explained Simply

A reusable recipe, not a complete kitchen

An Agent Skill is a folder containing a recipe for an AI agent. The recipe says when to use it, what steps to follow and may include scripts or templates.

You can move that recipe between compatible agents. But the new kitchen still needs the right appliances, ingredients and keys: tools, credentials, network access and permissions. A database skill cannot access a database unless the host already has authorized database tools.

So reuse the workflow, but verify the environment. Read any bundled scripts, restrict permissions, pin the version and test the skill in each target tool before trusting it in production.

Conclusion

Agent Skills solve a real portability problem: teams can version reusable agent knowledge as ordinary directories instead of rewriting prompts for every session. The standard is small, inspectable and already supported by multiple coding-agent environments. Its limit is equally important: the portable unit is the workflow package, not the surrounding execution authority. Treat skills as dependencies, keep credentials and project configuration outside them, and test every host-specific boundary before claiming one workflow truly runs everywhere.
