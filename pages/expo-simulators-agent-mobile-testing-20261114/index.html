Expo Simulators Give Coding Agents a Phone to Test—But Not a Real Device

By Dekrov Published November 14, 2026 Updated November 14, 2026

Expo Simulators, launched on November 12, puts cloud iOS simulators and Android emulators within reach of coding agents and CI. It can return recordings, screenshots and logs as review evidence—but it is paid, does not provide physical devices, and a recorded run is not proof that an app is correct everywhere.

Start with the plain-English explanation ↓

Overview

On November 12, Expo announced general availability of Expo Simulators: remote iOS Simulator and Android Emulator sessions that an AI coding agent, CI job or teammate can start from the CLI, REST API or browser. Agents can install a compatible app build, interact with it, and return recordings, screenshots and logs. The change targets a real gap in vibe coding: an agent can edit a mobile app in a cloud sandbox but often cannot launch the platform runtime needed to see whether its UI actually works. Expo supplies that runtime; it does not supply a new model or guarantee that the agent chose meaningful tests. [1]

Technical Deep Dive

How it works

A session is a remote simulator or emulator attached to an Expo Services project. An agent starts it through EAS CLI or the REST API, installs an existing compatible build, drives the device with a controller, gathers evidence, then stops the session. The service moves device compute away from the agent's laptop or sandbox; the code, test plan and interpretation of results still belong to the team.

Official statement

Expo's launch post establishes the product's GA status, the advertised session artifacts, plan access and per-minute rate. It is a vendor description, not an independent benchmark. It does not establish how reliably a particular agent will test an app, how much review time teams save, or whether a simulator run predicts behavior on physical devices. [1]

The agent stays the agent

Expo Simulators is not a coding model or a replacement for Claude Code, Codex or Cursor. The coding agent still edits the repository and decides what to test. Expo provides the remote device runtime and a control path. The current docs describe EAS CLI, a REST API, browser preview, and automation through agent-device, Argent or Appium. That makes the feature closer to hosted test infrastructure than to another IDE or agent harness. [2] [3]

From a code change to review evidence

The documented loop is concrete: check account availability; choose a compatible app build; start a named session; install and open the app; drive controls; capture screenshots for static states or a recording for motion; then stop the session. In a cloud job, Expo says the agent needs an authenticated EAS CLI and an EXPO_TOKEN. The session page can keep the recording and artifacts available to reviewers after the device session ends. [3]

That is useful for a narrow but important slice of mobile work: a cloud agent can reproduce a reported screen bug, test a checkout flow, or show an animation without borrowing the developer's local simulator. Expo documents support for projects built with Expo, React Native, SwiftUI, Kotlin, Flutter, Unity and other frameworks, provided the app can run on the corresponding simulator or emulator. A build is still required; this is not a source-code-to-app service. [1] [2]

Price, access and session limits

Expo's launch materials say the service is generally available on its paid Starter, Production and Enterprise plans. The published rate is $0.10 per simulator minute for either platform, with 60 minutes included per month on those plans through 2026. The usage docs say a paid session can run for at most 115 minutes; the session clock starts when the device is ready, and queue time does not count toward its startup timeout. Check the live pricing page before adopting it because plan details can change. [1] [4] [6]

A closed terminal or finished CI job does not necessarily stop a non-interactive session. Expo recommends explicitly stopping sessions and setting maximum-duration and idle-time limits. That matters when an agent retries, loses its connection or exits early: without a guardrail, the device can keep running and consuming minutes until its time limit. [4]

The evidence has an access-control cost

Session previews and controller tokens are sensitive. Expo's security documentation says project viewers can see session details, and a View Only member can retrieve controller tokens for an active session through APIs. A public preview link can let anyone with the link view and control the running device. Keep generated .env.eas-simulator and agent configuration out of source control and CI artifacts; do not print remote configuration in logs. A recording can be helpful evidence, but it may also expose account data, test credentials or private UI content unless the test environment is sanitized. [5]

What a Recording Proves—and What It Does Not

A recording can show what happened in one named test session on one selected simulator, alongside the screenshots or logs the run captured. That makes a pull request easier to inspect than a claim that “the agent tested it.” It is still evidence of a run, not evidence that every path was covered or that the same result holds on real hardware. The quality of the proof depends on the agent's instructions, the test data, the build and the chosen checks. [1] [3]

Community Signal Is Still Early

The product launched only two days before this review. The Reddit result available in the source check was Expo's own announcement, not an independent user evaluation; it is not enough to infer adoption or quality. I found no independently published comparison of agent success, reliability or total cost against local simulators. The honest current read is that the workflow is documented and available, while its real-world performance still needs longer-term developer evidence. [7]

Explained Simply

A simulator is software that imitates a phone's operating system on a computer. An emulator does the same for Android. Expo runs one remotely so an AI agent can open an app and tap through it, even when the agent itself runs on Linux or in a cloud workspace.

Think of the coding agent as a builder who can change a room's layout but cannot walk into the room to inspect it. Expo Simulators gives the builder a remotely controlled test room and sends back a video of the inspection. A developer can review that evidence without installing every tool on their own laptop.

It can help test app flows and layouts, reproduce a bug, and run several isolated checks in parallel. It does not give the agent a real phone, test every device model, or prove that a change is safe just because a recording exists. Use physical-device testing where hardware behavior matters, ask the agent for a specific observable result, and stop each paid session when it finishes.

Conclusion

The verified change is infrastructure: Expo now offers remote mobile runtimes, automated controls and reviewable session artifacts to paid plans. Its strongest fit is a cloud coding agent or CI pipeline that needs repeatable UI checks without hosting simulators locally. The trade-offs are per-minute billing, account and project setup, session-token handling, and the absence of physical devices. As of November 14, launch materials provide no independent benchmark showing that agent-led simulator checks reduce defects or review time; treat the feature as a new test surface, not an autonomous QA guarantee.
