GitHub Will Block pull_request_target by Default on December 2

By DekrovPublished November 15, 2026Updated November 15, 2026

GitHub is moving a long-documented Pwn Request risk from guidance into platform policy. Public repositories without an applicable custom Actions event policy will have pull_request_target blocked by default on December 2, 2026. A final two-hour brownout on November 16 offers a live warning—but the protection has important scope and bypass limits.

Start with the plain-English explanation ↓

Overview

GitHub announced that, beginning December 2, 2026, its default workflow execution policy will block pull_request_target in affected public repositories unless an applicable Actions event policy explicitly permits it. The second scheduled brownout runs on November 16 from 16:00 to 18:00 UTC—17:00 to 19:00 in Rome—when covered workflow attempts will fail with an annotation instead of executing. [1]

The change applies to public repositories on GitHub Free, Team and Enterprise Cloud. It does not apply to private or internal repositories or GitHub Enterprise Server. It also does not replace a matching event policy that administrators have already configured.

Official rollout

Until enforcement, the default policy normally stays in evaluate mode: runs continue, while policy insights show what would later be blocked. During the brownout, the default is temporarily enforced. After the window it returns to evaluation until December 2. [1]

Technical Deep Dive

Why the two PR events have different trust

Propertypull_request from a forkpull_request_target
Workflow definitionPR merge commitBase repository’s default branch

Token and secretsRead-only token; repository secrets withheldElevated base-repository trust; secrets may be available
Safe default useBuild and test untrusted changes with fork restrictionsMetadata actions such as labeling, triage and authenticated comments
Critical failureUsually lacks privileged credentialsExplicitly checking out and executing attacker-controlled PR code

GitHub’s current security guide explains the trust model: pull_request_target is safe only while the workflow and checkout stay on trusted base-branch code. The Pwn Request flaw appears when a privileged job switches to the fork’s head commit and then executes it. [2]

The Pwn Request attack chain

  1. An attacker opens a fork pull request and changes executable project content: tests, build scripts, package manifests or install hooks.
  2. A base-branch workflow starts through pull_request_target, receiving the privileged token and any configured secrets.
  3. The workflow explicitly checks out the PR head, fetches it manually, downloads an attacker-controlled artifact, or otherwise places untrusted content in the job.
  4. A seemingly normal command—npm install, tests, a compiler, a Makefile or a third-party action—executes attacker-controlled behavior.
  5. The payload can exfiltrate secrets, poison releases, alter repository content or abuse the privileged token.

GitHub Security Lab documented this pattern from real workflow vulnerabilities in 2021. The warning remains current: explicit checkout plus execution of an untrusted PR under pull_request_target can compromise the repository. [3]

What the new policy actually blocks

Workflow execution protections form an allowlist layered at enterprise, organization and repository levels. Event rules can permit or reject triggers including push, pull_request, pull_request_target and workflow_dispatch; actor rules can separately control who may trigger targeted workflows. [4]

The default December rule is not a code rewrite and not a universal kill switch. If a public repository already has an applicable event policy, that configured policy governs it. Private and internal repositories remain outside the default. A repository administrator can explicitly allow the event—ideally only for named workflow files—so unsafe logic can still exist after the rollout.

A practical migration audit

  1. Inventory the trigger. Search .github/workflows for pull_request_target, then inspect policy insights for would-be-blocked runs.
  2. Prefer pull_request. If the job only builds, lints or tests fork code and needs no secrets, use the lower-trust event.
  3. Separate trust zones. Run untrusted compilation in an unprivileged workflow. If a privileged follow-up is unavoidable, pass narrowly defined data—not executable files—and validate every artifact boundary.
  4. Reduce authority. Set minimal permissions:, expose only necessary secrets and avoid persistent self-hosted runners with internal network reach.
  5. Audit hidden execution. Treat package installation, tests, build configuration, generators and downloaded artifacts as code execution.
  6. Keep cache read-only. GitHub now restricts default-branch cache writes for this trigger; opting back into write-capable cache mode reintroduces cache-poisoning risk.
  7. Allow only the narrow exception. If the trigger is genuinely necessary, target the specific workflow in an applicable Actions event policy instead of broadly allowing the event.

GitHub’s administration guide recommends layered, clearly scoped policies rather than one broad rule. Administrators can evaluate a protection before enforcement, inspect matches in Insights, then narrow the targeted repositories, workflows, actors and events. [5]

Agentic Workflows adds another guard

GitHub Agentic Workflows v1.2.0 separately changed its compiler so fork use with pull_request_target requires explicit opt-in. The release also hardened ZIP extraction and run-step expression sanitization. [6]

Current Agentic Workflows documentation defaults the trigger to same-repository pull requests. Exact fork or trusted-owner patterns can be admitted; a wildcard "*" is rejected in strict mode unless features.dangerously-allow-pull-request-target-forks-all: true is set. Even then, the warning remains. Actor authorization and checkout restrictions still apply independently. [7]

What the Default Does Not Prove

A blocked trigger prevents one class of privileged execution; it does not certify the remaining Actions configuration. Command injection through issue titles or branch names, mutable third-party actions, overbroad tokens, unsafe workflow_run artifact handling and persistent self-hosted runners require separate controls.

GitHub also documents an explicit allow-unsafe-pr-checkout: true escape hatch for actions/checkout. Custom Git commands and third-party checkout logic are outside that single protection. Neither a policy exception nor a checkout flag makes fork code trustworthy. [2]

Explained Simply

The visitor and the master key

A normal fork pull request is like letting a visitor demonstrate their machine in an empty room. GitHub withholds the building’s master keys.

pull_request_target is different: it lets trusted automation use the base repository’s keys so it can label, comment or manage the pull request. The danger begins if that trusted automation brings the visitor’s machine into the privileged room and switches it on.

GitHub will now lock that privileged door by default for affected public repositories. Maintainers can still unlock it, so the real fix is to remove unnecessary uses, keep untrusted builds separate and grant the smallest possible permissions.

Conclusion

The November 16 brownout is the last live rehearsal before GitHub’s December 2 enforcement. Public-repository maintainers should use it to find affected runs, but a failed run is only the signal. The durable remediation is architectural: use pull_request for untrusted code, reserve pull_request_target for trusted metadata operations, separate privileged follow-up work, and scope any policy exception to the smallest workflow possible.
